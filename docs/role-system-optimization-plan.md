# wiseSpace 角色系统优化计划

## 目标

把当前的“会话角色选择”从一组内置 prompt，逐步演进成一个可管理、可扩展、可自定义、可解释的角色系统。

这套系统要解决四个现实问题：

1. 内置角色数量有限，无法覆盖所有使用场景
2. 用户对角色的工作方式、输出要求和适用边界缺少透明认知
3. 角色只能选择，不能按个人或团队需要做调整
4. 角色定义和实际会话执行提示词之间缺少明确映射

## 当前状态

当前已经具备：

- 会话级角色切换
- 角色提示词注入到会话 system prompt
- `wiseSpace Local` 与普通会话共用同一套有效 system prompt 解析
- 角色管理页
- 对话页最多显示 6 个角色
- 内置角色详情查看

当前仍存在的问题：

- 角色详情还是直接展示 prompt，本质上更像原始配置而不是产品化说明
- 内置角色不可编辑
- 无法新建自定义角色
- 无法区分“内置角色”和“用户角色”
- 角色详情和最终生效提示词不是同一视角
- 角色来源和演进路径没有结构化记录

## 设计原则

### 1. 内置角色与用户角色分层

内置角色用于提供稳定默认值，用户角色用于适配个人或团队习惯。

不建议直接修改内置角色原件，优先采用：

- 复制内置角色
- 生成用户角色副本
- 在副本上修改

这样可以避免：

- 升级时覆盖用户改动
- 无法区分默认模板和自定义模板
- 调试时难以复现问题

### 2. 角色详情与角色提示词分离

角色详情页应该展示结构化信息，而不是直接暴露一整段原始 prompt。

推荐拆成这些字段：

- `角色定位`
- `适用场景`
- `工作方式`
- `输出要求`
- `边界与禁忌`
- `来源`

其中：

- 详情页给人看
- 最终 prompt 给模型用

两者可以由同一份角色定义生成，但展示层和执行层不应完全耦合。

### 3. 角色系统优先服务会话页主路径

角色系统的核心入口仍然应该在会话页，而不是角色管理页本身。

角色管理页负责：

- 浏览
- 查看详情
- 筛选显示
- 编辑
- 创建

会话页负责：

- 快速切换
- 查看当前角色
- 必要时查看角色详情

## 参考策略

`agency-agents` 可以作为角色设计的重要参考来源，但不建议直接复制原文。

可参考的内容：

- 角色分类方式
- 角色职责边界
- 角色交付导向
- 工作流程表达方式

不建议直接照搬的内容：

- 面向 Claude Code 的工具假设
- 过重、过长且与 `wiseSpace` 本地执行场景不完全匹配的 prompt
- 与当前 UI 和权限模型冲突的行为定义

建议做法：

- 借鉴 `agency-agents` 的角色结构
- 使用 `wiseSpace` 的执行模型重写角色定义
- 保留来源说明，避免角色演进失真

## 优化路线

### Phase 1：详情产品化

目标：

- 让角色详情更像产品能力说明，而不是配置文本

内容：

- 把角色详情从整段 prompt 改成结构化展示
- 增加 `来源` 字段
- 增加 `适用场景` 与 `边界` 展示
- 增加 `查看最终生效内容` 入口

产出：

- 用户能看懂“这个角色适合什么时候用”
- 用户能分清“角色定义”和“最终生效 prompt”

### Phase 2：角色可编辑

目标：

- 允许用户按自己的方式调整角色

内容：

- 新增“复制并编辑”能力
- 生成用户角色副本
- 支持编辑：
  - 名称
  - 简介
  - 角色定位
  - 适用场景
  - 工作方式
  - 输出要求
  - 边界与禁忌
  - 最终 prompt 模板

产出：

- 用户可以从内置角色演化出自己的版本

### Phase 3：自定义角色

目标：

- 用户可以从零创建自己的角色

内容：

- 新建自定义角色
- 删除自定义角色
- 控制是否显示到会话页
- 支持排序

产出：

- 角色系统从“预设库”升级为“可管理资产”

### Phase 4：角色来源与模板体系

目标：

- 让角色来源清晰、后续演进可追踪

内容：

- 给每个角色增加来源字段：
  - `builtin`
  - `adapted-from-agency-agents`
  - `user-defined`
- 记录角色版本和最近修改时间
- 后续允许导入角色模板

产出：

- 内置角色、借鉴角色、自定义角色边界清晰

### Phase 5：角色与总结/记忆联动

目标：

- 让角色不只影响回复，还影响沉淀

内容：

- 会话总结按角色使用不同结构
- 研究类角色默认偏总结结构
- 审查类角色默认偏问题清单结构
- 文档类角色默认偏可交付文档结构

产出：

- 同一段会话在不同角色下能生成不同风格的沉淀结果

## 数据结构建议

建议后续把角色定义抽成统一结构，而不是只保留 `systemPrompt`：

```ts
interface RoleDefinition {
  id: string;
  source: 'builtin' | 'adapted' | 'user';
  name: string;
  description: string;
  category: 'general' | 'engineering' | 'review' | 'research' | 'product';
  position: string;
  useCases: string[];
  workflow: string[];
  deliverableStyle: string[];
  guardrails: string[];
  systemPrompt: string;
  visibleInChat: boolean;
  createdAt?: number;
  updatedAt?: number;
}
```

## 展示建议

角色管理页建议长期采用：

- 左侧角色列表
- 右侧详情面板

详情面板展示：

- 名称
- 分类
- 当前状态
- 来源
- 简介
- 适用场景
- 工作方式
- 输出要求
- 边界与禁忌
- 最终 prompt 预览

避免继续使用：

- 大面积重复卡片
- 详情与操作混杂在同一层列表里
- 只能看 prompt 原文而缺少解释

## 优先级建议

优先级从高到低：

1. 结构化角色详情
2. 复制内置角色并编辑
3. 自定义角色
4. 来源与版本字段
5. 角色与总结联动

## 实施建议

短期先做：

- 结构化详情展示
- 用户角色存储结构
- 复制并编辑内置角色

中期再做：

- 新建 / 删除用户角色
- 排序和分组
- 来源标识

后期再做：

- 角色模板导入
- 与总结、知识、记忆联动

## 结论

角色系统支持修改是有必要的，但推荐路线不是“直接修改内置角色”，而是：

- 保留稳定的内置角色
- 支持复制并编辑
- 支持自定义角色
- 逐步把角色从 prompt 集合演进成可管理资产

这条路线比继续堆内置角色更可持续，也更符合 `wiseSpace` 作为本地 AI 工作台的定位。
