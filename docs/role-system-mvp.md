# wiseSpace 角色系统 MVP 方案

## 1. 目标

为 wiseSpace 增加一个“角色系统”，让用户在创建或使用会话时，可以明确选择当前 AI 的工作角色，而不是只依赖模型本身的通用能力。

角色系统的目标不是简单切换一句 prompt，而是为会话提供：

- 更清晰的任务定位
- 更稳定的输出风格
- 更适合场景的工作流程
- 更可预期的交付结果

## 2. 为什么现在做

结合当前 wiseSpace 的产品方向，这个功能比继续扩展“任务中心”更有价值。

当前已经具备：

- 会话页为主路径
- 本地工作空间执行
- Agent 执行器选择
- 会话总结
- 本地文件、知识库、记忆沉淀能力

当前缺少：

- 用户在开始一段工作前，快速声明“这次你是什么角色”
- 不同任务类型对应不同的输出结构和工作方法
- 一套可复用、可管理、可扩展的角色预设体系

这正是 `agency-agents` 一类项目最值得借鉴的部分。

## 3. 产品定位

wiseSpace 角色系统应被定义为：

- 会话层的工作模式预设
- system prompt / workflow hint / deliverable style 的组合
- 比“模型选择”更偏方法论
- 比“执行器选择”更偏角色分工

它不是：

- 模型替代品
- 执行器替代品
- 一个新的复杂任务页面

## 4. 与现有结构的关系

### 4.1 与模型的关系

- 模型决定“能力上限”
- 角色决定“工作方式和输出风格”

### 4.2 与执行器的关系

- 执行器决定“由谁执行”
- 角色决定“以什么身份执行”

例如：

- 执行器：`wiseSpace Local`
- 角色：`前端工程师`

### 4.3 与 system prompt 的关系

角色本质上应落到会话级 system prompt，但不建议继续让用户直接编辑一大段 prompt 才能体现角色。

更合理的方式是：

- 角色驱动生成会话级 system prompt
- 用户仍可在高级模式下手动补充或覆盖

## 5. MVP 范围

### 5.1 第一版包含

- 内置少量高频角色
- 会话级选择角色
- 角色驱动 system prompt 注入
- 角色元信息展示
- 支持切换角色

### 5.2 第一版不包含

- 角色市场
- 在线同步角色
- 复杂角色编排
- 多角色协同执行
- 团队角色共享
- 角色版本管理

## 6. 第一版建议角色

不建议一上来导入几十个角色。第一版建议只做 4 到 6 个最高频角色。

建议内置：

### 6.1 通用执行助手

适用：

- 日常综合问题
- 不确定该选什么角色时

特点：

- 平衡分析、执行、总结

### 6.2 前端工程师

适用：

- 页面开发
- 交互优化
- 样式调整

特点：

- 重视 UI 结构、可读性、组件边界、响应式和可用性

### 6.3 后端工程师

适用：

- API
- 服务设计
- 数据处理
- 调试和排错

特点：

- 重视边界、异常、数据流、可维护性

### 6.4 代码审查员

适用：

- review
- 回归风险检查
- 变更质量判断

特点：

- 以问题发现和风险评估为主，不以直接产出代码为主

### 6.5 研究总结助手

适用：

- 调研
- 信息整理
- 方案对比
- 会话总结

特点：

- 重视结构化总结、对比和信息提炼

### 6.6 产品 / 文档助手

适用：

- PRD
- 文案
- 说明文档
- 流程梳理

特点：

- 重视受众、表达清晰度、结构和交付格式

## 7. 核心数据结构

第一版建议定义统一角色结构：

```ts
interface ConversationRolePreset {
  id: string
  name: string
  description: string
  category: 'general' | 'engineering' | 'review' | 'research' | 'product'
  systemPrompt: string
  workflowHints?: string[]
  deliverableStyle?: {
    defaultFormat?: 'plain' | 'bullets' | 'report' | 'checklist'
    emphasizeRisks?: boolean
    emphasizeFiles?: boolean
    emphasizeNextSteps?: boolean
  }
}
```

说明：

- `systemPrompt`：角色主约束
- `workflowHints`：补充角色行为规则
- `deliverableStyle`：控制输出风格

## 8. 会话侧挂载方式

建议挂在会话维度，而不是全局。

可选字段：

```ts
conversations.role_preset_id TEXT NULL
conversations.role_preset_name TEXT NULL
```

第一版也可以不立刻加表字段，先存在会话已有配置 JSON 或会话扩展字段里。

但从长期看，单独字段更清晰。

## 9. 与现有 AgentProfile 的关系

当前已经有：

- `AgentProfile`
- `default_runner_kind`
- `workspace_root`
- `permission_mode`

这些更偏执行环境。

角色系统建议不要直接塞进 `AgentProfile` 主结构里，而是：

- 角色属于会话内容层
- 执行器配置属于执行环境层

后续如果需要，也可以在 `AgentProfile` 里增加一个默认角色字段，但第一版不是必须。

## 10. 前端交互方案

### 10.1 入口位置

建议放在会话头部标题旁，或输入框附近的会话配置区。

推荐：

- 会话头部显示当前角色
- 点击打开角色选择菜单

展示形式：

```text
北森同步   [前端工程师 v]
```

### 10.2 创建会话时

第一版可不强制选择角色。

默认规则：

1. 用户上次使用的角色
2. 全局默认角色
3. `通用执行助手`

### 10.3 切换角色

切换后：

- 更新当前会话的角色预设
- 后续消息按新角色工作
- 不自动改写历史消息

### 10.4 显示内容

角色下拉项应显示：

- 名称
- 一句话说明
- 适用场景

## 11. system prompt 注入策略

建议采用三层拼接：

1. 全局默认 system prompt
2. 角色 system prompt
3. 会话自定义补充 prompt

顺序建议：

```text
Global Prompt
Role Prompt
Conversation Extra Prompt
```

这样既保证角色生效，又不丢用户已有自定义能力。

## 12. 第一版实现建议

### Phase 1

- 定义内置角色常量
- 会话页增加角色选择 UI
- 将角色 prompt 注入到会话 system prompt 组合逻辑中

### Phase 2

- 支持记住每个会话当前角色
- 在新建会话时继承默认角色

### Phase 3

- 会话总结支持按角色输出不同结构
- Agent 模式下根据角色调整默认行为

## 13. 对会话总结的联动价值

角色系统和“会话总结”天然适合联动。

例如：

- `研究总结助手`
  - 总结更偏结论、对比、资料归纳
- `代码审查员`
  - 总结更偏风险、问题、建议
- `前端工程师`
  - 总结更偏页面改动、组件、交互、视觉问题

所以后续总结功能可以复用角色上下文，而不必所有会话都走一种总结模板。

## 14. 对 Agent 执行的联动价值

角色系统后续可以影响：

- 默认输出结构
- 是否更倾向先分析再执行
- 是否更强调风险提示
- 是否更强调文件引用和改动说明
- 是否更强调结论与下一步建议

这会比单纯调整模型参数更贴近真实工作需求。

## 15. 为什么不直接照搬 agency-agents

不建议直接把外部仓库几十个角色原样搬进 wiseSpace。

原因：

- 数量过多，第一版会分散注意力
- 外部模板更偏 prompt 文件集合
- wiseSpace 需要的是“产品化的角色系统”，不是一堆散落的 markdown 文件

更合理的路径是：

- 先做角色 schema
- 先做少量高频内置角色
- 后续再考虑兼容外部角色模板导入

## 16. 验收标准

满足以下条件即可认为 MVP 成立：

- 用户可以为会话选择角色
- 切换角色后后续回复风格能明显变化
- 不需要手工编辑大段 system prompt
- 内置角色数量少但清晰
- 与模型、执行器的职责边界明确

## 17. 建议结论

建议立即按 MVP 路线推进，但控制节奏：

- 先做会话级角色选择
- 先做 4 到 6 个高频角色
- 先只接 `system prompt` 注入

不要一开始做：

- 角色市场
- 外部导入
- 多角色编排
- 复杂自动化

先把“角色选择 -> 输出变化 -> 总结可联动”这条主链打通，wiseSpace 的可用性会明显上一个台阶。
